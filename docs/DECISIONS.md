# Design decisions

Wherever the spec left a choice open, the simplest defensible option was taken. Each one is
recorded here with its reason.

| # | Date | Decision | Why |
|---|---|---|---|
| 1 | 2026-10-01 | Vendor (copy) the basketBuddy collectors unchanged into `collectors/vendor/`, with SHA-256 sums | Self-contained and reproducible; the research data provably comes from the same code as the app. Owner's choice |
| 2 | 2026-10-01 | Replace `session_store.py` with a no-op stub; do not copy `db.py` | The original reads and writes the production Supabase project. This project must never touch it |
| 3 | 2026-10-01 | Do not copy any session or cookie file; sessions are re-minted locally into gitignored files | Live auth cookies are secrets. Owner's choice |
| 4 | 2026-10-01 | Local SQLite (`data/grocery.sqlite`) with portable SQL | No need for a server; spec allows it; keeps production untouched |
| 5 | 2026-10-01 | Extra columns beyond the spec: `observations.chain_product_id`, `search_rank`, `priced_store_id`, `source`, `extra` (JSON); `stores.ruca`, `anchor_zip`, `coord_quality`, `address`; `items.search_term`, `walmart_id`, `target_tcin`, `costco_ic_id`, `tj_sku`; `collection_failures.raw_path` | Needed to identify products without UPCs, to audit store specificity and coordinates, and to keep chain-specific promo text without inventing columns per chain |
| 6 | 2026-10-01 | Wrappers bypass `price_all_*` and `find_best_purchase` and call the low-level fetch functions | Those functions reduce results to the single cheapest product and merge promo with regular price |
| 7 | 2026-10-01 | Pacing: 1 request at a time per domain, ≥ 2 s + jitter between requests, 2 retries with exponential backoff on transport errors only, **stop the chain for the run on the first WAF block** | Spec ground rule 2 and "do not escalate". The upstream code rotates proxies and IPs on blocks; we never do |
| 8 | 2026-10-01 | Walmart and Costco stores are anchored to the sampled Target stores' ZIPs | No Walmart or Costco directory exists; building one would add traffic. Pairing also helps the cross-chain comparison |
| 9 | 2026-10-01 | Costco location id = Instacart `retailerLocationId`; coordinates = anchor ZIP centroid | Instacart returns no address; the item ids carry the location id, so store specificity can be checked per row |
| 10 | 2026-10-01 | Never use the vendored Costco "expanding metro" fallback | It substitutes a different city's warehouse |
| 11 | 2026-10-01 | Store specificity per row: Target `price.location_id == store`; Walmart any `fulfillmentSummary.storeId == scoped store`; Costco item location prefix == shop location; Trader Joe's never | These are the retailers' own statements of where a price applies (verified live). Target prices about 10% of items at location 3991; Walmart returns many marketplace and fulfilment-centre listings |
| 12 | 2026-10-01 | `is_promo = 1` iff the retailer reports a regular or "was" price strictly above the current price; multi-buy deals and clip coupons stay in `extra` and do not change `price` | Spec rule; multi-buy prices are conditional on quantity, so they are not a shelf price |
| 13 | 2026-10-01 | Every returned product is stored against the item query that returned it; which product "is" the item is decided at analysis time via owner-confirmed ids and UPCs | Keeps the raw evidence; matching can be redone |
| 14 | 2026-10-01 | UPCs come only from retailer product pages (`resolve_items.py`); never typed in by hand. Candidates are ranked by a transparent heuristic and **reviewed by the owner** | Spec "never fabricate"; the heuristic got Cheerios wrong (different size) in the smoke test |
| 15 | 2026-10-01 | `items.csv`: `cross_chain = 1` means *intended* cross-chain; actual matching requires equal UPCs at both chains | UPCs are unknown until resolution |
| 16 | 2026-10-01 | Urbanicity from the 2020 ZIP-level RUCA primary code: 1 urban, 2–3 suburban, 4–10 rural | Standard public classification, available for every ZIP, with no extra data pulls |
| 17 | 2026-10-01 | Target frame locations come from the store address Target reports (locate pass); the slug geocodes are used only as a provisional fallback | The slug geocodes are wrong for ~25% of stores |
| 18 | 2026-10-01 | Walmart coordinates from OpenStreetMap features whose `ref` is the store number | Verified on both smoke-test stores; ~3,900 Walmart features carry `ref` |
| 19 | 2026-10-01 | Hill estimator: report k = 5% of n as primary, with the stability-rule k (on k ≤ 15% n) and k = 10% as sensitivity | Simulation: on \|t₃\| data the stability rule over-reaches into the body (95% CI coverage 0.22–0.78) while k = 5% covers 0.84–0.92; all are fine on exact Pareto data |
| 20 | 2026-10-01 | GPD threshold at the 90% quantile of \|d\|, reported on the shape scale ξ | Comparable across chains; ξ ≤ 0 (no power tail) is possible and must not be forced into an α |
| 21 | 2026-10-01 | The database can be rebuilt entirely from `data/raw/` (`collectors/reparse.py`); failures are mirrored to `data/raw/snapN/_failures.jsonl` | Spec: "parsing can be redone"; reproducibility from raw data |
| 22 | 2026-10-01 | The smoke-test failure row for Trader Joe's was restored by hand into `_failures.jsonl` (marked as such) after the DB was rebuilt during a schema change | The event happened and was seen in the console; missingness is data |
| 23 | 2026-10-01 | Python venv lives outside OneDrive (`C:\Users\laksh\.venvs\groceryStatistics`) | Avoids OneDrive syncing tens of thousands of package files |
| 24 | 2026-10-02 | Drop Trader Joe's from the study | HTTP 403 on Day 1 and only a single national web price, so it has no store-level variation to study. Costco (Instacart, analysed separately) is the near-uniform control. Owner's choice |
| 25 | 2026-10-02 | Snapshots run at full scope (≈250 anchor stores × 58 items), one process per chain in parallel, sharing one snapshot id; SQLite in WAL mode | Each chain is a separate domain at ≤ 1 request / 2 s, so per-retailer load is unchanged. The window exceeds the spec's "few hours" (≈ 9–12 h); start/end times are recorded, and per-row `observed_at` allows a time-of-collection check. Owner's choice |
| 26 | 2026-10-02 | The analysis uses only the snapshots listed in `config/analysis.yaml`; snapshot 1 (smoke test + item-resolution searches at one Columbus OH store) is excluded | Snapshot notes do not survive `reparse`; an explicit list is unambiguous |
| 27 | 2026-10-02 | Target soft-blocked (HTTP 435 at every store) after ~115 locate requests at 2 s; the locate pass was stopped by hand after 10 refused requests. Response: (a) a per-domain circuit breaker in `DomainPacer`: 6 consecutive failed requests to a domain = block, chain stops (`GS_MAX_CONSECUTIVE_FAILURES`); (b) Target domains paced at ≥ 5 s (`GS_DOMAIN_INTERVALS`); (c) wait a few hours, resume with the normal session; if blocked again, skip the locate pass and draw the sample from located stores + ZCTA-checked slug geocodes | Ground rule: never keep hitting a retailer that refuses us, never escalate. Previously a soft block was a TransientError: retried, logged, and skipped store by store indefinitely. Owner's choice on (c) |
| 28 | 2026-10-02 | Replace 15 redundant grocery items with 15 national-brand non-grocery items (household, personal care, OTC health, baby, pet); total stays 58 | Same identical-UPC logic applies to anything both chains stock; non-grocery adds a department contrast for the tail and factor analyses at no extra traffic. Electronics, toys and apparel excluded: mostly online/ship-to-home, so rarely store-specific. Owner's choice |
| 29 | 2026-10-02 | Walmart also paced at ≥ 5 s after a px-captcha at ~80 requests (2 s pace) during the resolution searches; the chain stopped automatically on the block | Same rule as #27. Two chains pushing back at 2–2.5 s means the full-snapshot pace must be ~5 s, so 250 × 58 takes ≈ 22 h per chain; scope to be revisited with the owner |
| 30 | 2026-10-02 | Kroger wrapper (`collectors/kroger.py`, official API) added as an **optional** chain, not in the default snapshot. Measured on the certification host: with the full search term, 15 / 58 items return anything; with 2-word fallback terms, 10 / 58 have a good name-and-size match with a price (Houston store). Many products carry no price; one Columbus price was dated 2023-08-31. Production credentials returned 401 | The certification catalog is a small test subset and cannot support a 58-item cross-chain comparison. With production credentials (`KROGER_BASE_URL=https://api.kroger.com/v1`) the same code can run as a full chain. UPC conversion verified (Kroger 13-digit id → UPC-A equals Target's UPC for Barilla) |
| 31 | 2026-10-02 | `config/store_sample.csv` is written in a seeded random visit order (`visit_order`, seed + 1), not stratum by stratum | The runner visits stores in file order. Sorted by stratum, a run stopped part-way (e.g. by a block) would have covered whole regions and missed others; in random order any prefix is a random subsample of every stratum |
| 32 | 2026-10-02 | Module B store effects are centred and constrained to mean zero within each chain; the spatial field is centred over stores | Otherwise adding c to every store effect and subtracting c from every product effect leaves the likelihood unchanged; in simulation this ridge gave R-hat 1.11 and ESS 38, after the change R-hat ≤ 1.01 and ESS > 700 for all three models |
| 33 | 2026-10-02 | PyMC sampling uses the NumPyro (JAX) NUTS backend; the MILP uses PuLP 4 with the HiGHS solver | No C++ compiler on this machine (PyMC's default backend would be very slow); PuLP 4 no longer bundles CBC |
| 34 | 2026-10-02 | Target soft-blocked again at 04:15 after ~47 searches at 5 s. Target is stopped: no product pages, no locate pass. The store sample was redrawn from 114 located stores plus ZIP-area-checked directory coordinates (the approved fallback). Snapshot 2 (the first main snapshot) was started for **Walmart and Costco only**; Target is pending the owner's decision on scope | Target tolerates ~50–115 requests per session window, so a 250 × 58 Target snapshot (~14,500 requests) is not feasible without escalation, which is ruled out. Walmart and Costco are anchored to the sample ZIPs and do not depend on Target data. Stores are visited in random order, so the run can be stopped at any point |
| 35 | 2026-10-02 | `resolve_items --fetch-chains` limits product-page fetches to the listed chains | Lets UPC resolution run for Walmart while Target is blocked, without overwriting Target's candidate scoring |
| 36 | 2026-10-02 | Kroger certification catalog re-checked by exact UPC (Walmart-page UPCs via `filter.productId`): 19 of 58 in the catalog, 16 priced at the Houston store, 4 at the Columbus store. Kroger is added to snapshot 2 for the **25 items** it carries (by UPC or by search), tagged `kroger_ce` | Three methods agree that the test catalog is partial; restricting to the carried items keeps the run within the 10,000/day Products limit |
| 37 | 2026-10-02 | ALDI (`collectors/aldi.py`) and Meijer (`collectors/meijer.py`) added to snapshot 2 at the owner's request. ALDI: Instacart white-label on `www.aldi.us`, same parser and per-row store check as Costco, tagged `aldi_ic`. Meijer: own store locator (nearest full store within 50 km; never the upstream default store 130, never the proxy walk) plus Constructor.io search; multi-buy offers not treated as promotions; UPC from `ean` | Separate domains, so each gets its own pacing. Probe: Meijer prices differ between stores for the same product (so they are store-specific), and the EAN gives UPCs matching Target and Kroger; ALDI rows carry the shop's location id |
| 38 | 2026-10-02 | Module B rebuilt as a **two-part (observed hurdle) model**: part 1, is the price exactly the chain's list (modal) price, a logistic GLMM with store effects; part 2, if not, log(price/list) is Student-t with a store-level mean (non-centred store effects; + HSGP spatial field in M2). M0 (Normal) kept as reference; LOO compares only M1 vs M2. Fitted on the **contiguous US** (HI/AK excluded and counted) | On real data 91% of Walmart prices equal list and 89% of departures are upward. A single Student-t residual hit its bounds (R-hat ~3); a latent mixture label-switched (R-hat ~4); whether a price is at list is observed, so a two-part model has no latent label. One Honolulu store made the non-spatial model bimodal (store effect vs heavy tail). On the contiguous US both two-part models converge (R-hat ≤ 1.01, ESS ≥ 500); the re-done simulation recovers 13/16 parameters in 90% intervals (the rest close) |
| 39 | 2026-10-03 | Kroger **production** API adopted (owner's production app; keys `KROGER_CLIENT_ID2/SECRET2`, `KROGER_BASE_URL=https://api.kroger.com/v1`), all 58 items, paced at 9 s (≤ 10,000 calls/day). Test-host data relabelled chain **`kroger_ce`** (DB rows updated; `reparse` maps pre-cutover `kroger` envelopes/failures to `kroger_ce`, cutover 2026-10-03T01:45Z); the test-host run was stopped | Production check: 40/58 Walmart UPCs in the catalog and 37 priced at one Columbus store (test host: 19 and 4). Same store ids in both environments, so one chain label would have let the resume check skip production work and the unique key drop production rows |
| 40 | 2026-10-03 | **Balanced-prefix visit order** (`sampling/visit_order.py`) replaces the random shuffle: systematic interleaving across strata (key (i+u_h)/n_h) with farthest-point order within each stratum. The sample itself is unchanged | Collection often stops part-way, and what remains is a prefix. In the new order every prefix is proportional across strata to within 1 store, and spread out: at 25% of the list, 38 states vs 25 and 220 km vs 61 km median nearest-neighbour distance; at 50%, all 12 strata and 41 states. Chains already mid-run (Costco, ALDI) continue on the old order and will reach all 250 anyway |
| 41 | 2026-10-03 | `snapshot --budget N`: each chain stops cleanly after N item queries per run (logged as a planned stop) and resumes next run. Target is collected in short sessions (32 queries, 16 items whose UPC agrees across chains) instead of one long run | Target pushed back after ~50–115 requests per session; staying well below that volume, with long gaps between sessions, respects its limits without any change of identity or method |
| 42 | 2026-10-03 | **Local session stash** (`collectors/session_stash.py`, `data/sessions/`, gitignored): one stored session per chain **per network (public IP)**, restored at the start of each run; saved after the first successful request. A block (explicit challenge or 6-failure streak) starts a **12 h cooldown** for that chain, during which no session is created, swapped or reused. A failure while the machine's IP changed mid-run stops the chain *without* a cooldown, and the next run uses that network's session | Owner's observation: on campus the public IP changes between buildings, and bot-protection services can challenge a valid session used from a different IP, even in ordinary browsing. Keeping per-network sessions avoids mistaking that for a block. Only one session per network is kept, since several on one IP would only serve rotation; no new sessions after a block (owner's rule). The production Supabase pool is never used |
| 43 | 2026-10-03 | **One spare session per chain per network; one switch per run.** On a challenge (explicit or a 6-failure streak), the runner switches once to this network's spare (made in advance through the normal session start, never during a cooldown). If the spare's first request also fails (two sessions in a row), it is treated as an IP block: stop + 12 h cooldown. A later refusal after a successful switch also stops the chain. No third session, no proxies, no session created after a refusal. Applies to Target, Costco and ALDI (sessions swappable in place); Walmart (per-store browser scoping) and Meijer/Kroger (no cookie session) still stop at the first block. Every switch is logged (`session-switch:` in `collection_failures`) | Owner's finding from basketBuddy testing: genuine blocks target the IP, not the cookie, so one failing session can be bad luck. The rule distinguishes a bad cookie from an IP block with one bounded check; the logged outcomes let the write-up report how often a switch rescued a session versus preceded a stop |
| 44 | 2026-10-03 | **Simple session policy** (supersedes #42–43): each run starts with a **fresh** session and a fresh **spare**, both made through the collectors' normal session start before anything is refused. The first is used as long as it works; on a refusal, switch once to the spare; if the spare's first request also fails (two sessions in a row), stop and pause the chain for 12 h. No session is ever made after a refusal. Every session with at least one successful request is **archived** per network (`data/sessions/<chain>/<network>/<timestamp>/`), for the record only. A basket design that tried further stored sessions after a refusal was written and then discarded in favour of this simpler rule | Owner's choice of a simple rule; the owner's earlier line (no new sessions after a block) is kept by making the second session at run start rather than in response to a refusal. The two-in-a-row stop separates a bad cookie from an IP-level block with one bounded check |
| 45 | 2026-10-03 | The post-block pause **escalates** instead of a fixed 12 h: 3 h after a 1st block, 6 h after a 2nd in a row, then 12 h, then 24 h (`GS_BLOCK_PAUSE_SCHEDULE`). A run with successful requests and no block resets the streak (it never shortens a pause already running) | Owner's experience that 3–4 h is usually enough; observed here too (Target was refused 37 min after a block, but accepted a budgeted session the next day). Escalation keeps repeated blocks from being retried at a short interval |
